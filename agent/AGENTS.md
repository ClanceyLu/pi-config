# 全局开发规则

## 修改前同步最新代码

- 在 Git 仓库中开始修改前，先核验仓库、当前分支、远端及其跟踪分支，检查暂存、未暂存、未追踪文件和未完成的合并；不能猜测远端或目标分支。
- 跟踪目标明确时，先获取远端状态，检查当前分支的远端跟踪分支是否有本地尚未包含的新提交；有则执行 `git pull --ff-only`，成功同步后再修改，没有则直接继续。
- 默认在当前分支开展开发，不自动创建或切换分支，也不自动创建 worktree。仅当用户明确要求时，才创建或切换分支、创建 worktree；创建时使用用户指定的基准，未指定时使用已核验的最新远端主分支提交，并记录基准 SHA。
- 本地存在暂存、未暂存或未追踪改动本身不构成阻塞，无需因此请求确认；保留现有工作，继续检查远端并执行任务，不覆盖无关改动。
- 仅在跟踪目标不明确、同步被本地改动阻挡、分支分叉、存在冲突或未完成的合并、远端不可达时，报告实际阻塞，取得明确处理决定后再继续；不得为同步而自动 stash、丢弃改动、rebase、强制重置或强推。不得静默跳过同步并声称代码已是最新。
- 同步授权仅用于读取远端及快进当前已核验的跟踪分支，不包含推送、部署或扩大任务范围；用户明确要求离线或保持指定版本时遵循该要求，并说明未同步的状态。非 Git 目录不执行远端同步。

## 临时文档与资料存放位置

- 任务过程中产生的临时 Markdown 等文件，包括规划、计划（plan）、分析、调研、重构方案、草稿、报告及生成或收集的参考资料，统一放在对应项目根目录的 `tmp/` 下；目录不存在时按需创建，可按任务建立子目录。
- 不将这些临时文件直接写入项目根目录、`docs/` 或其他现有正式文档目录，也不将其加入正式文档的导航或索引。
- 只有用户明确要求纳入正式文档，或任务本身就是维护正式文档时，才将应长期维护的内容写入对应文档位置；过程中产生的计划、分析和参考资料仍放在 `tmp/` 下。

## 文档以当前事实为中心

- 编写或修改 README、使用说明、架构和开发文档时，以最终实现为准，直接描述当前行为、架构、数据来源和使用方式，让读者无需了解修改过程即可理解系统。
- 实现要求发生变化后，重写受影响的段落，并清理失效描述、示例、图表、命令和配置说明；不得仅追加更正句或删除声明，保留相互矛盾的旧内容。
- 避免反复使用“已删除”“不再使用”“改为”“现在只”等依赖历史背景的表述，优先写出完整、可独立理解的当前事实。例如，写“应用从本地数据库读取和保存数据”，而不是反复强调“云端已删除，数据不再来源于云端”。
- 历史变化仅在影响升级操作、兼容性、使用判断或理解重要决策时保留，并集中放入适当的迁移指南、变更记录或决策记录，避免在多处重复；不为记录修改过程额外创建文档。
- 必要的能力边界和限制应直接说明，并解释对使用者的实际影响；不得为了回避否定句而省略有用信息。
- 交付前检查本次涉及的文档是否与当前实现一致，移除仅用于证明已遵循提示词或完成修改的过程性说明。

## UI 文案与用户提示词隔离

- 用户提示词中的实现要求、验收标准、限制条件和解释性描述，默认只用于指导实现，不得直接或改写后作为面向最终用户的 UI 文案。
- 不得为了说明已遵循要求，而在界面中添加诸如“最终结果不会自动保存”“按要求未实现某功能”“这是演示页面”等元说明。
- 只有当用户明确要求在界面展示该文案，或该信息确实是产品使用所必需的状态、警告、错误或操作说明时，才可以展示；此时应使用符合产品语境、面向最终用户的文案。
- 交付前检查本次新增或修改的所有可见 UI 文案，移除源自提示词但不属于产品需求的元信息。
