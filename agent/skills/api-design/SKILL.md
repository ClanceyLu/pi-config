# API 设计与演进规范

以消费者需求和现有契约为起点，交付一致、安全、可演进且能验证的接口。默认面向 HTTP/JSON；若项目使用 GraphQL、gRPC、事件或语言库 API，保留其协议与工具链，只采用适用的兼容性、安全与验证原则，不擅自改造成 REST。

## 1. 先读契约，再确定设计

- 遵循仓库说明及 Git/修改授权；检查现有路由、schema、handler、鉴权、客户端/SDK、测试、网关与 CI，找齐调用方及生成代码入口。
- 确认消费者、核心操作、资源归属、权限边界、数据规模与失败场景。影响方案的未知项才询问，不为简单接口索取完整平台蓝图。
- 复用项目已有路径、字段命名、错误结构、分页和版本策略。区分协议/标准要求、项目明确约定与可选建议；外部组织的 MUST 不自动成为项目硬性规则。协议条文或工具版本不确定时核验当前适用版本，不能声称未验证的合规性。
- 需要改变既有客户端行为、暴露敏感数据或产生不可逆副作用时，先说明兼容性/安全影响并取得必要决定；不借设计任务自动部署、迁移或发布。

## 2. 资源、方法与 HTTP 语义

- 以稳定业务资源而非数据库表或内部函数组织 API；REST 集合通常使用复数名词，路径嵌套只体现必要归属。不能自然表达为 CRUD 的业务动作采用项目现有 action 约定，不硬凑资源。
- `GET`/`HEAD` 不触发客户端请求的业务写操作；GET body 的互操作性差，查询使用项目支持的参数或独立搜索操作。
- `POST` 用于创建或执行操作；`PUT` 表达目标资源表示的替换语义；`PATCH` 明确补丁格式与局部更新语义，不把 PUT 静默实现成 PATCH。
- 幂等指重复请求的预期服务端效果相同，不要求每次响应状态或正文完全相同；DELETE 首次成功、再次 404 并不自动违反幂等性。
- 使用真实 HTTP 状态，不统一返回 200 再靠正文表示失败。常见选择如下，服从适用协议和现有契约：

| 情况 | 常见响应与契约要点 |
| --- | --- |
| 创建完成 | `201`，按接口需要提供新资源标识及 `Location` |
| 仅已接受异步处理 | `202`，说明后续查询方式与终态，不伪装已完成 |
| 成功且无正文 | `204`，不能再发送 JSON 正文 |
| 请求格式/校验失败 | `400` 或项目明确区分的 `422`，提供可操作信息 |
| 缺失或无效认证 | `401`，按认证方案提供适用的 `WWW-Authenticate` challenge |
| 已认证但无权限 | 通常 `403`；为隐藏资源存在性可按安全策略返回 `404` |
| 资源不存在/状态冲突/前置条件失败 | 按原因选 `404`/`409`/`412`，不混为服务器错误 |
| 限流/暂时不可用 | `429`/`503`，适用时提供 `Retry-After` |

## 3. schema 与请求响应

- schema 明确类型、格式、长度/数值范围、必填、可空、默认值、只读/只写及未知字段政策；输入校验和输出兼容性分开考虑。
- 明确“字段缺失”“显式 null”“空字符串/空集合”的差异，尤其 PATCH 中保留、清空与删除的语义。未知输入不能未经筛选映射到内部模型造成批量赋值漏洞。
- 使用专门的请求/响应表示或项目等效的字段白名单，不直接暴露数据库/内部对象中的敏感属性；不为每层机械复制相同 DTO。
- ID 对客户端保持不透明；跨语言整数精度、十进制金额、币种/单位、时间戳时区及精度均显式约定，不假定 JSON 浮点能精确表示全部整数或金额。
- 命名及集合包装遵循项目，不把 `snake_case`、`camelCase`、统一 `{data: ...}` 包装或强制 HATEOAS 当作通用标准。
- 默认不返回无业务需要的敏感字段，不用响应字段的“前端不展示”代替权限控制。

## 4. 错误契约

- 错误提供稳定机器可读标识、面向调用者的说明，以及必要的字段位置/请求关联信息；客户端不靠解析自然语言消息决定业务行为。
- 保持既有错误格式；新接口无既定格式时可采用 RFC 9457 Problem Details（`application/problem+json`），不为对齐样例强行重写已发布契约。
- 采用 Problem Details 时，`type` 标识问题类型，`title`/`detail` 用于说明，扩展字段承载业务错误码或校验项；不能只改 Content-Type 而不遵循结构与语义。
- 区分认证、授权、输入、业务冲突及服务故障；错误不能泄露堆栈、SQL、密钥、内部地址或其他租户数据，日志与响应按各自受众脱敏。

## 5. 认证、授权与资源边界

- 使用项目已有认证方案与 TLS，不自创签名/令牌机制；校验适用的 token 签名、发行者、受众、有效期与权限，凭证不放 URL。
- 每次对象读写和列表查询都检查调用者对资源/租户的权限；拥有 scope 或知道 ID 不代表拥有该对象，不信任客户端提交的 owner/tenant 字段。
- 批量、搜索、导出、嵌套对象、字段级读写和管理员操作保留相同权限边界，避免只保护单资源接口。
- 对请求体、分页大小、批量数、上传、超时及并发施加适用限制；外部 URL、文件路径和重定向目标按需防 SSRF、路径穿越及协议滥用。
- Cookie 会话考虑 CSRF；CORS 不等于认证或授权。OpenAPI 中的 security 声明也不能代替服务端 enforcement。

## 6. 列表、幂等与并发（按业务需要）

- 可能增长的集合从首次发布考虑分页：明确默认/最大页大小、排序与稳定的唯一 tie-breaker、过滤语法及结束标志，不默认计算昂贵总数。
- 大集合/频繁变化数据通常优先游标；小型、需要页码跳转的数据可用 offset。游标不透明不等于加密或授权，校验其查询/租户绑定；不承诺无快照保障的绝对无重复/遗漏。
- 对可能被重试且有副作用的操作明确重试条件。业务需要幂等键时，定义键的主体/操作作用域、有效期、请求指纹、相同键不同内容的冲突、并发中请求及结果重放行为。
- 去重记录与业务效果需原子协调，或采用项目已有可靠机制；进程内缓存、客户端不重复点击或自动重试不等于跨实例幂等，更不保证端到端 exactly-once。
- 并发写入有丢失更新风险时采用现有版本号、ETag/`If-Match` 或事务机制；前置条件不匹配返回符合契约的错误，不静默覆盖。
- 客户端只在已知安全的操作/失败条件下重试，使用有上限的退避与抖动并遵循适用的 `Retry-After`；不对所有 4xx 或所有 POST 无条件重试。
- 只有业务需要才设计缓存、异步操作状态或 webhook；缓存不能泄露用户数据，异步操作要可观察失败与终态，不顺带建设未请求的平台能力。

## 7. 兼容性与版本演进

- 分别检查请求、响应、生成 SDK 与实际消费者：新增必填输入、删改字段、改变类型/单位/语义、缩紧输入限制、改变错误码或分页行为都可能破坏兼容性。
- 新增响应字段通常比删改安全，但严格反序列化/SDK 仍需验证；新增响应 enum 值可能破坏穷尽匹配，不把“只增加”自动视为兼容。
- 客户端对契约允许的未知响应字段保持容忍；服务端未知输入是否拒绝按现有政策明确，不将“忽略一切未知字段”当成安全默认值。
- 优先兼容扩展。需要不兼容变化时明确新旧契约、迁移路径、弃用期限及消费者通知，沿用项目版本机制，不强制新增 `/v1` 或 Azure 风格 `api-version`。
- 同步更新受影响的 schema、服务端、客户端/SDK、示例、测试和变更说明；生成文件通过现有生成器更新，不仅修改生成结果。

## 8. 契约、验证与交付

- HTTP API 用项目已有 OpenAPI/等效契约描述；沿用 design-first 或 code-first 的单一来源，不能手写和生成各维护一份互相漂移的真相。
- 版本服从现有生成器/校验器支持范围，不强制升级到最新 OAS；例如 3.0 的 `nullable` 与 3.1 的 JSON Schema 空类型表达不能机械混用。
- 描述路径/参数位置、schema、媒体类型、成功与相关错误、鉴权、分页及实际支持的 header；提供唯一稳定的 `operationId`（采用时）和符合 schema 的最小示例。
- 优先使用仓库已有 lint、schema 校验、生成及兼容性 diff 入口，不为规范新增一套依赖。契约校验与真实行为测试缺一不能互相冒充。
- 按本次风险补测试：正常路径、无效/边界输入、未认证、对象/跨租户越权、错误映射；涉及分页、幂等或并发时再测其关键重复/竞争/失败场景。
- 设计交付简述资源/操作、请求响应、错误与权限、适用的分页/幂等/兼容性决定；实现交付给出实际变更、验证命令/结果及未验证项。审查按影响报告位置、消费者影响与最小建议。
