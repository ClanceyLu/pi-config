# 编写有价值的测试

测试保护当前业务行为、对外契约和真实风险，而不是复刻实现、记录修改历史或凑数量。用能证明行为正确的最小测试，复用项目已有框架和约定。

## 1. 先明确要证明什么

- 阅读需求、被测代码、调用入口及相关已有测试，明确输入、操作、预期结果和真实风险。预期来自业务规则或对外契约，不能照抄当前实现的输出。
- 每个场景都应回答：“哪一种具体错误会使这个测试失败？”答不出来就不要写。不要为标准库自身的默认行为或样本生成器单独增加测试，除非它们承载了应用特有的契约。
- 优先覆盖主路径，以及会造成数据丢失、越权、重复执行、误操作或错误计算的边界。按风险选择空值、无效输入、跨日、并发、失败恢复等场景，不穷举没有价值的组合。
- 写缺陷回归测试时，尽可能先用最小样本复现原问题，再验证修复。不要把错误的现有行为写成预期。

## 2. 选择最小但真实的验证层级

- 纯业务规则优先单元测试；存储、迁移和组件协作用集成测试；关键用户操作及页面交互用 UI 测试。
- 已有测试覆盖相同行为、入口和边界时，补充必要断言或样本即可，不复制整套流程。不同入口存在独立校验或接线风险时，不能以底层测试替代入口验证。
- 一个测试围绕一个行为组织；允许用连续步骤证明同一行为，例如保存、重新加载和核对结果。名称必须准确描述实际验证内容。
- 不为测试引入不必要的依赖、通用框架或生产配置。测试替身用于控制外部依赖，不把被测核心逻辑本身替换掉。

## 3. 构造可复现且隔离的样本

- 每个测试独立建立状态，不依赖执行顺序、其他测试残留、真实用户档案或开发者已有账号。文件与数据库使用隔离位置，并按项目惯例清理。
- 时间相关核心测试显式传入时钟或日期；区分民用日期、UTC 时间戳和本地日历，按场景使用明确的时区，并覆盖必要的跨日与夏令时边界。
- UI 场景的前提应在实际运行日期成立，不假设今天总是工作日、计划日或同一个月。需要固定日期时使用项目已有的测试时钟入口，不为此扩大产品功能。
- 参数化场景应实际进入不同路径；注意输入是否在执行前被统一归一化，避免把同一场景跑两遍却声称覆盖了两个边界。
- 模拟错误应准确命中目标失败点；数据写入失败时还要检查原有数据和状态，而不只检查是否抛错。

## 4. 断言可观察的结果与契约

- 验证真实结果，而不只是代码执行过、对象存在或按钮可见。比如验证保存颜色，就重新加载后检查颜色值；验证重复请求，就检查返回结果及记录数量、内容未被重复修改。
- 声称验证持久化、恢复或重启时，使用新的读取边界或实际重启，并检查对应字段，不能只复查同一份内存状态。声称验证编辑结果时，检查实际修改的值。
- 对 JSON 等结构化数据解析后检查字段或语义，不匹配无关的缩进、空格和键顺序；字节本身属于协议或原文件保全要求时，才逐字节比较。
- UI 测试优先验证用户操作及其结果。只对明确的产品文案、无障碍、触控范围和布局要求检查具体表现，不把旧控件标识或偶然页面结构变成永久契约。
- 不因刚删除某个按钮或功能，就新增“旧控件不存在”的断言。反向断言应有当前业务含义，例如无权限不能执行、取消后不保存、滑动不触发打卡、失败不显示成功或覆盖原文件。
- 截图是人工检查证据，不等于自动视觉回归通过。没有图像比较机制时，不声称验证了像素、颜色或视觉一致性；应检查相关状态、可操作性或必要的布局边界。
- 同步优先等待状态、条件或事件，不为截图或碰运气增加固定休眠。平台防误触、协议时序或硬件校准确需等待时，保留并简要说明原因。

## 5. 验证并如实交付

- 运行受影响的测试，确认新增测试确实被发现和执行；检查新名称及筛选器、脚本和配置的引用。日期逻辑按风险在不同时区复跑。
- 测试失败时区分产品缺陷、样本错误和环境限制；不能靠删除有效断言、跳过失败项、反复重试或扩大容差制造通过。真实的硬件或服务限制应明确记录，不冒充已验证。
- 不把测试任务当作修改产品行为、真实用户数据、权限、部署或提交推送的额外授权。
- 报告实际执行范围、失败、跳过与未验证项。区分初次全量运行和修复后的局部重跑，不能把部分重跑通过说成最终版本全量通过。

交付前自查：名称与断言是否一致？样本是否满足前提？目标行为被破坏时是否真的会失败？是否重复验证已有场景？结论是否超出了实际执行的证据？
